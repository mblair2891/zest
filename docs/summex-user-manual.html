1. Introduction & product overview

1.1 What Summex is

Summex is a hospitality operating system for bars, restaurants, multi-vendor food halls, and food truck pods. It combines front-of-house POS, kitchen display routing, labor timekeeping, multi-merchant settlement, inventory intelligence, guest ordering surfaces, and a SaaS-style HQ for operators who run multiple sites or vendors under one roof.

The product tagline is Service, sharp. The platform is built by Michael Blair and Andy Baida.

1.2 Core concepts

ConceptMeaning in Summex
Location / buildingA physical site (restaurant, hall, or truck pod). Settlement and pads are location-scoped.
Vendor / merchantA food or beverage operator inside a hall or pod. Menu items and KDS tickets carry a vendor id.
Check / orderA guest bill. In a hall, one check can hold lines from many vendors; the guest still pays once.
TicketA kitchen/bar fire group sent from a check, routed by station and vendor.
Access level (role)Determines which screens appear after login (Owner, Manager, Server, etc.).
Host cutBuilding operator share of vendor sales, configured in settlement settings.
Red-flag clock-outClock-out outside the minutes window after last closed ticket → supervisor review.
PadA truck parking/power slip in truck-pod mode.

2. Getting started

2.1 Sign-in & PIN pad

Owner Manager Server Bartender Host Kitchen Busser

The login screen shows the Summex mark, PIN dots, and a numeric pad. Enter your 4-digit staff PIN. On success you land on the home screen for your role (for example, servers land on Floor; kitchen on Kitchen KDS).

  1. Open Summex on the terminal, tablet, or browser preview.
  2. Enter your PIN (demo PINs listed below) or use a Quick login chip.
  3. Confirm your name and access level in the top-right header.
  4. Use only the menu items shown — unauthorized tools are hidden.

2.2 Quick login by access level

Below the PIN pad, Quick login by access level shows one representative employee for each role. Each chip displays:

  • Employee name
  • Access level badge (Owner, Manager, Server, …)
  • Short description of what that level can do
Tip: Use these chips when training or demos so you can switch personas without memorizing every PIN.

3.2 Owner

Owner

Purpose: Full control of the site and platform demo surfaces including SaaS.

Home: HQ. Typical tools: SaaS, HQ, truck pod, settlement, integrations, labor, AI stock, all FOH/BOH modules, settings.

When to use: Configuration, multi-vendor payouts, supplier strategy, viewing every report, training all roles.

Manager

Purpose: Run the building day-to-day without platform SaaS billing controls.

Home: HQ. Includes settlement, labor rules, inventory AI, cash, menu, staff, promotions, purchasing, floor editor, etc. No SaaS console.

When to use: Open/close, comps/voids approval, period close, payroll readiness, 86 items, coaching floor.

4. Floor & tables

Owner Manager Server Host Busser

4.1 Floor map

The Floor view shows tables by section with status colors (available, seated, ordering, ordered, check printed, paid, dirty, reserved). Section filters narrow the map. Live counts summarize the room.

4.2 Seat a party

  1. Tap an available table.
  2. Enter guest count; confirm.
  3. Summex opens a dine-in check assigned to the signed-in server and jumps to Order.

4.3 Open an existing check

Tap any occupied table to reopen its order in the Order screen.

4.4 Dirty → available (busser / host / server)

After payment, tables become paid then can be cleared to dirty. Tap a dirty table to mark it clean (available).

4.5 Merge tables

OwnerManagerServer

  1. Enable merge mode on the floor toolbar.
  2. Tap the primary table (keeps the check).
  3. Tap the secondary table to merge in.
  4. Lines and guest counts combine; child table is linked under the primary.

Use unmerge when the party splits or the combine was a mistake.

4.6 Transfer check between tables

  1. Enable transfer mode.
  2. Tap the table that owns the open check.
  3. Tap an available destination table.

4.7 Bar tabs from floor

Open a named bar tab when the guest is not seated at a dining table. The check type becomes bar tab and appears in takeout/tab lists.

4.8 Floor plan editor

OwnerManager

Drag tables, edit labels, seats, section, and shape (round / rect / bar). Add dining or bar seats. Remove tables that have no open check. Layout changes are saved in the demo store for this browser.

5. Ordering & checks

Owner Manager Server Bartender

5.1 Order screen layout

  • Left / main: category tabs and menu grid (filterable by vendor in hall mode).
  • Check rail: lines with seat, modifiers, send state, voids/comps.
  • Totals: subtotal, tax, auto-gratuity when party size qualifies, balance.

5.2 Add items

  1. Select category (or All).
  2. Optional: set active seat number for seat-based ordering.
  3. Tap a menu item. If modifiers are required, complete the modifier dialog.
  4. Item appears unsent on the check.
Happy hour: When enabled in settings and within the configured window, items with happy-hour prices ring at the discounted amount automatically.

5.3 Multi-vendor (food hall) lines

Each menu item can belong to a vendor (kitchen, bar, noodle stall, etc.). Lines show vendor short names. Sending routes tickets to the correct vendor KDS. Payment remains a single guest transaction (see Chapter 10).

5.4 Send / fire

  • Send — fires unsent lines that are not held; creates kitchen/bar tickets grouped by station, vendor, and course.
  • Hold — keep a course until you fire it.
  • Fire course — release held items for a course.

5.5 Void, comp, notes, seats

Select a line to void (manager PIN when required), comp, adjust quantity (unsent), add notes, or reassign seat. Voids and comps write to the shift audit and sales adjustments.

5.6 Discounts & check notes

Apply percent or fixed discounts with a reason / promo code. Check-level notes print context for the team.

5.7 Print check & pay

  1. Print check — marks table status “check” for the floor map.
  2. Pay — opens payment dialog (card, cash, gift, etc.).
  3. When balance hits zero, check closes; table moves toward paid/dirty.

Closing a check records the server’s last closed ticket time, which Labor uses for red-flag clock-out logic (Chapter 11).

10. Multi-vendor settlement

Owner Manager

10.1 The model (important)

A location is a building. Inside it, several food/beverage vendors fulfill items. Guests may order across vendors on one table visit. The server enters one check; items route to each vendor’s production. The guest pays once (card or cash). Summex does not rely on Stripe Connect-style per-item routing to decide who is paid.

Instead, at period end the platform calculates each vendor’s due amount.

10.2 Configuration

  • Period type: daily, weekly, biweekly, monthly, or custom days.
  • Card fee percent deducted from card-attributed product sales.
  • Host cut on/off; percent of gross or fixed per vendor.
  • Tax remitter: host vs vendor (policy flag for reporting).
  • Current period start timestamp.

10.3 Live preview

Settlement view shows open-period totals per vendor: gross, card vs cash attribution, fees, host cut split, electronic payout, and cash due.

10.4 Close period

  1. Review live preview and cash distribution report.
  2. Close period — freezes a settlement snapshot.
  3. Mark paid when e-payouts / cash envelopes are complete (demo status).
Demo note: ACH payout initiation is simulated. The ledger math and reports are real in-app logic.

10.5 Vendor portal

Vendors can inspect their sales, 86 their items, and view the last settlement row without seeing other merchants’ full bank details.

11. Labor, clock & payroll rules

Owner Manager

Module: Labor. Staff time flags also appear under Staff for simple in/out, but Labor owns compliance rules.

11.1 Published shifts & clock-in window

Settings define how many minutes before and after scheduled start a punch is allowed. Outside the window, clock-in is blocked unless a manager forces override (demo messaging).

11.2 Red-flag clock-out

Settings define clock-out red-flag minutes measured from the employee’s last closed ticket/check.

  • Clock-out within the window → timecard auto-approved.
  • Clock-out outside the window (or no tickets) → pending review, supervisor alert.

Use the Labor simulators (“ticket 5m ago” / “45m ago”) to train the two paths.

11.3 Supervisor queue

Approve as-is or correct punches (demo correction trims dangling time). Alerts resolve when handled.

11.4 Daily closeout

Configured time (e.g. 04:00). Running closeout forces any still-open clocks to pending review so the day can end cleanly.

11.5 Payroll

  • Auto-export — only if every finished punch is approved / auto-approved / corrected.
  • Manual — hold period for offline payroll processing.

Export payload is a demo JSON for processors like ADP (no live transmission).

11.6 Staff screen

Simple roster with tips/sales counters and quick clock toggle (does not replace Labor rules UI).

12.3 AI inventory audits

OwnerManager

Example: bar receives 4 bottles of vodka. Through the week, cocktail recipes consume ml pours. The AI multiplies sales × recipe to estimate theoretical use, expected on-hand, variance vs count, and par status.

  1. Open AI stock.
  2. Run daily, weekly, or monthly audit.
  3. Review variance notes (spillage, over-pour, receiving errors).
  4. Adjust par / reorder points; receive stock when product arrives.

Works the same for food recipes (patties, buns, wings, etc.).

12.4 Suppliers

20. Workflows by access level

20.1 Owner — open a multi-vendor day

  1. Quick login as Owner (or PIN 9999).
  2. HQ: confirm locations open; glance online queue.
  3. Settlement: verify period settings and host cut.
  4. Labor: confirm clock windows and red-flag minutes.
  5. AI stock: run yesterday’s audit if week-end.
  6. Integrations: confirm payroll/SMS partners connected (demo).

20.2 Manager — service + close

  1. Login Manager → HQ.
  2. Cash: open shift float.
  3. Coach floor; approve voids/comps with manager PIN.
  4. Labor: resolve red flags before payroll.
  5. Settlement: close period; distribute cash report; mark e-payouts paid.
  6. Cash: close drawer; review audit.

20.3 Server — table from seat to pay

  1. Login Server → Floor.
  2. Seat table → add items from multiple vendors if hall → send.
  3. Optional Drink AI for beverage upsell.
  4. Print check → pay card/cash → thank guest.
  5. When done for night, Manager uses Labor for clock-out rules.

20.4 Bartender — rail service

  1. Login Bartender → Bar KDS.
  2. Bump tickets; open tabs via Order/Takeout.
  3. Use Drink AI for undecided guests.
  4. 86 items on Menu/Stock when bottles die.

20.5 Host — door

  1. Login Host → Waitlist.
  2. Add walk-ins with quotes; notify; seat to floor.
  3. Manage reservations as parties arrive.

20.6 Kitchen — line

  1. Login Kitchen → Kitchen KDS.
  2. Start and bump tickets; watch vendor labels in hall mode.
  3. Consult recipes; tick checklists on open/close.

20.7 Busser — turns

  1. Login Busser → Floor.
  2. Find dirty tables; mark clean for host/server seating.

21. Troubleshooting & FAQ

I don’t see HQ / SaaS / Settle

Your access level hides those tools. Sign out and login as Manager or Owner.

“Summex hit a snag” / React error

Use Reset demo data & reload on the error screen, or clear site data for the Summex URL. This drops corrupted local demo state.

Card payment failed / no deposit

Card rails are simulated. The UI records a successful demo tender but does not move real money.

Clock-in denied

You are outside the early/late window relative to the published shift. A manager must adjust rules or force clock-in policy.

Clock-out red flagged

You clocked out later than N minutes after your last closed check. Supervisor approves or corrects in Labor.

Vendor didn’t get a ticket

Confirm the menu item has the correct vendor id and that you pressed Send. Check that vendor’s KDS filter.

Settlement looks wrong

Attribution is by merchandise share, not tax. Host cut and card fees apply per configuration. Close period only after the service day is complete.

AI inventory variance

Check recipe pour sizes, unrecorded comps/spillage, and whether receiving was logged.
